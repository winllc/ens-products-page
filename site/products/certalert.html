CertAlert · Certificate expiration visibility

Available

Every certificate in your directory, and who answers for it.

CertAlert reads the people and servers out of your LDAP directory, parses every certificate they publish, and puts the results in searchable tables. It knows the points of contact for each server, alerts them before a certificate expires, and reports on the whole directory — so an expiring certificate is a planned renewal, not a surprise.

How it works

The directory is the source of truth. CertAlert is the index over it.

  1. Scheduled sweeps read the directory. Nightly jobs read every person and every server with paged searches, so large directories are read completely rather than stopping at the server’s size limit. Where the directory publishes a changelog, CertAlert follows it too and picks up a replaced certificate within seconds instead of overnight.
  2. Every certificate is parsed once and cached. Subject, issuer, serial, validity, key and signature algorithms, subject alternative names and a SHA-256 fingerprint are stored, so no question needs the directory again. A re-sync of an unchanged directory writes nothing.
  3. Status is kept current. Every hour, each certificate is checked again as valid, expiring soon, critical or expired, and each person and server is rolled up to the certificates it still depends on.
  4. The right people hear about it. Points of contact get an in-app notification when a certificate changes state, and a daily email round-up of what is coming due.

What it does

Search tables

People and servers, filtered any way

Separate tables for users and servers, sorted and filtered by certificate status, expiry window, point of contact or project, or narrowed to “only mine.” Expand a row for its certificates, contacts and recent history.

Points of contact

A named owner for every server

The directory’s own serverPOC is read and matched to people. Contacts can also be added in CertAlert, and a nightly sync never overwrites them. From any person you can list every server they are responsible for.

Notifications

One alert, to everyone who needs it

Status-change notices appear under the bell in the app, and a daily expiry round-up is emailed to each contact, one message per person rather than one per certificate. A dry run shows what would be sent, and administrators can use their own email templates.

Metrics

Where the organization stands

What is due in 7, 30 and 90 days, key sizes and signature algorithms in use, issuance trends and issuing authorities, revocation counts, and how many people have been told.

Projects

Group what gets renewed together

Group servers and people into a project, so “forty certificates expire this month” becomes “the payroll migration expires this month.” Both tables filter by project.

Audit trail

What happened, and who did it

Each entry has a history: when it was discovered, which certificates were published or withdrawn, status changes, alerts sent or failed, and edits to its contacts.

Beyond the expiry date

Revocation checks

A scheduled job asks the issuing authorities which certificates they have revoked. A certificate reported stolen in March is flagged, even though its expiry date is still years away.

What the server is actually serving

A server’s endpoint check connects over TLS and compares the certificate it presents with the newest one in the directory. This catches a renewal that was issued but never installed.

Risky names

Wildcards, broad wildcards such as *.gov, certificates with many names or domains, and bare hostnames are flagged so they can be reviewed.

Directory clean-up

An optional job removes certificates from the directory once they have been expired or revoked for a set time, so other systems that read the directory stop finding them.

Security

Certificate sign-in, matched exactly

A client certificate is matched by its SHA-256 fingerprint against the certificates the directory publishes for that person, not by pattern-matching a subject name. Removing the certificate from the directory removes the access. Directory password sign-in is the fallback.

Built for the IC directory schema

Built for the IC IdAM Full Service Directory object classes (icOrgPerson, icOrgServer), and every attribute name can be configured for other schemas.

Classification banners

Optional fixed banners at the top and bottom of every page, for deployments that must show the classification of what is on screen.

No outside dependencies

The whole interface is served from the application itself, with no CDN, so it works on networks that have no internet route.
