Directory Services Portal · Web front end for LDAP

Available

Your directory’s own schema, as forms people can use.

Directory Services Portal puts a web front end on LDAP directories, including those with custom, non-standard schemas. Administrators build forms for any object class, publish them as directories scoped to one part of the tree, and decide who can read or edit each one. Every user gets a profile page showing where they appear and what they can update themselves — without anyone needing an LDAP browser.

How it works

Administrators set it up once, and people use it from any browser.

  1. Load the schema. Read it straight from the directory, including non-standard object classes and attributes, or import OpenLDAP schema files and cn=config LDIF. Add display names and descriptions, or define elements the server does not publish.
  2. Build a form. Pick the object classes and the editor suggests their attributes, then warns about schema problems before they reach the directory. Fields can be text, text areas or drop-downs, including drop-downs filled from a directory search. For example, choose a manager by name and store their DN.
  3. Publish it as a directory. Link the form to a base DN, a scope and an optional filter. The portal only reads or writes entries inside that part of the tree. Choose read/write, or a read-only “white pages” that nobody can write through, administrators included.
  4. Grant access. Give users or directory groups view, or view-and-edit, access to each directory. A matrix shows every grant at a glance.

For the people in the directory

Directories

Search, browse and edit

Each directory is a searchable, sortable list. Entries can be viewed, created, edited and deleted according to the user’s access. Only changed values are written, and changing the naming attribute renames the entry.

My profile

Everywhere you appear, in one place

Each user sees every directory that lists them and can update the fields marked self-service, such as a phone number, without raising a ticket.

Validation

Checked twice before it reaches the directory

Required fields, single-value rules, allowed options, formats (email, phone, URL, number, DN), patterns and length limits are checked in the browser and again on the server.

Sign-in

Directory password or smart card

Users sign in with their own directory password, or with a client certificate such as a CAC or PIV card. Each certificate is mapped to exactly one directory user. The portal can also be set to accept certificates only.

Security

Certificates checked before mapping

Validity dates, client-authentication key usage and, optionally, the chain to your CAs and revocation (OCSP or CRL). Optionally, the certificate must also be the one published on the user’s entry.

Namespaces enforced on the server

Every DN is parsed and checked against the directory’s base, scope and filter, and writes are limited to the form’s writable fields. User input in filters is always escaped.

Hardened sessions

HttpOnly, SameSite=Strict session cookies, a new session ID at sign-in, CSRF protection on every change, login throttling, and password attributes that are never sent to the browser.

What you need to run it

Directory Services Portal technical summary
Component Detail
API Spring Boot 4 on Java 21, using the UnboundID LDAP SDK over a pooled service-account connection
Web client A static React build served by nginx, which forwards /api to the API so the browser sees a single origin
Directory Any LDAP / LDAPS server, with StartTLS supported. The service account needs read access to the schema and the exposed parts of the tree, and write access wherever users edit
Storage No database. Forms, directories, grants and custom schema are kept in a single JSON configuration file
Authentication Password sign-in verified by an LDAP bind; optional mutual TLS, ended at the web proxy or at the API
Deployment Separate containers for the web client and the API, plus a Docker Compose stack with a demo OpenLDAP server
